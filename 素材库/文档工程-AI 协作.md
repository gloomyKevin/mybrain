## 一 · 为什么这是一个真问题

### 1.1 AI 协作放大的旧问题
项目文档以前就两个极端（Doc1）：
- **极端 A**：几乎没文档，知识全在代码、聊天记录、个别人脑子里
- **极端 B**：建了很多文档，但只是静态堆积，没职责、没演进机制

AI 辅助开发**放大**了这个问题：
- AI 可以梳理调用关系、分析业务流程——但你**不能指望它每次都重新翻一遍代码**，再和你对话几十轮才勉强明白
- 没给它清晰边界时，它会"模仿着写"，看起来像那么回事，**悄悄给你带两个 bug**（Doc1 原话）

### 1.2 文档工程要解决的是三个问题（不是"多写文档"）
Doc1 的根本表述：
- 什么信息应该被记录？
- 这些信息应该记录到哪里？
- 当代码和业务变化时，哪些文档必须跟着变？

所以是**知识组织问题**，不是**文档数量问题**。

### 1.3 诚实痛点（Doc5 #7 · Lucoshin）
**"项目大了，上下文太长了，这些东西自己就懒得看了。"**

任何文档工程方案都要正面回答这个 —— 否则它只是纸上谈兵。

## 二 · 核心心法 / 立场

| # | 心法 | 来源 | 解读 |
|---|---|---|---|
| A1 | 文档工程不是制造更多文件 —— 是让知识具备**结构、边界、演进路径、可追溯性** | Doc1 | 全文最核心的一句 |
| A2 | 不只是给人看，也是给 AI 看 —— 让 AI 知道该在哪里落点 | Doc1 | AI 协作时代的新变量 |
| A3 | **结构先成立，内容后生长** | Doc1 | 反"先补全再启动"陷阱（对 OPC 的反推迟主义有强共鸣） |
| A4 | 让模板来自真实生产，不是来自想象中的完美结构 | Doc1 | 模板设计原则 |
| A5 | Markdown 是 AI 时代的源代码 | Doc3 | 文档驱动派立场 |
| A6 | 编程重点从"写代码"转向"写需求文档" | Doc3 | 同上 |
| A7 | 代码 > 注释 > CLAUDE.md > 文档 | Doc4 · zhedream | 轻派代表 |
| A8 | 文档多了也是屎山 | Doc4 · zhedream | 轻派代表 |

### 2.1 A1 和 A7/A8 不是对立
看起来重派（A1）和轻派（A7/A8）在吵，实际上：
- **重派**说的是"有结构才能让 AI 懂"
- **轻派**说的是"长了 AI 根本不看"
- 两派合起来看 → **AI 要看且能看懂的文档，必须有结构、且足够短**
- 这就接到了 Token 哲学（§八）

## 三 · 分类体系（5 套并存，不是互斥）

### 3.1 Doc1 的三层分离（最底层，最常被引用）

| 层 | 回答什么问题 | 读者 | 例子 |
|---|---|---|---|
| **规范层** | 文档怎么写、目录怎么分、哪些改动触发哪些文档更新、模板放哪 | 团队 + AI | AGENTS.md 的 7 个模块、DOC_GOVERNANCE.md |
| **过程层** | 这次任务做了什么、改了哪些模块、做过哪些验证、是否涉及 DB/接口/业务变更 | 开发执行 + 后续追溯 | `task-2026-03-11-xxx.md` |
| **成品层** | 系统现在对外暴露什么、接口/业务规则/架构边界 | 所有人（产品/测试/实施/研发） | `API.md`、`BUSINESS_RULES.md`、`ARCHITECTURE.md` |

**核心判词**：这三层**混在一起就会失去"可推理性"**（详见 §四）。

### 3.2 Doc2 的 4 分类（按是否上 Git）

| 类别 | 上 Git | 理由 |
|---|---|---|
| 工作流框架生成的运行过程文档 | ❌ | 短生命周期、产出量大、GitHub 里没有价值 |
| 成品文档（业务/接口/需求） | ✅ | 最终要关注的；AI 新需求的知识库 |
| 与 AI 头脑风暴的前期文档 | ❌ | 讨论完就可以丢 |
| 代码规范 + bug 踩坑记录 | ✅ | 可持续成长的；团队协作时防踩同一个坑 |

**joyousoda 的补充金句**：
> "过程文档 AI 也是可以检索的（相信 AI），我平常让他翻出来和领导对线当时是谁让我改的：包括 git 记录、issue 记录。"
>
> —— **过程文档的"维权"用途**（§十二深挖）

### 3.3 Doc3 的 OpenSpec 4 文档（一次需求拆 4 份）

| 文档 | 回答什么 |
|---|---|
| `proposal` | 为什么要做 |
| `specs` | 需求和场景 |
| `design` | 技术设计 |
| `tasks` | 具体实施清单 |

**配套工具**：OpenSpec（Fission-AI/OpenSpec） + Codex CLI 作为落地入口。

### 3.4 Doc5 · akirann 的 2 文档（最小可用体系）

| 文档 | 职责 |
|---|---|
| 需求文档 | 用户需求 / AI 对需求圆满的逻辑 / AI 对需求的大概实现流程 |
| 设计文档 | 根据需求文档 + 实现内容，详细记录**如何实现** / **怎么实现** / **修改了哪些文件** |

**模板结构**（详见 §十四）：
- 需求文档：背景与目标 / 核心需求 / 业务逻辑 / 约束与边界 / 依赖与前置条件
- 设计文档：技术方案 / 关键实现（伪代码 / 接口设计表 / 数据结构变更表） / 文件变更清单 / 验收条件 / 风险与注意事项

### 3.5 Doc5 · Lucoshin 的 6 类文档矩阵（最多的一派）

| 文档类型 | 用途 |
|---|---|
| **待办文档** | 记录和 AI 讨论过程，防忘 |
| **界面交互逻辑文档** | 丢给其他 AI 分析前端设计是否规范、提意见 |
| **问题解决方案文档** | 项目规则里让 AI 每次解决问题就记录"排查思路 + 解决方法"；下次相似问题先找找 |
| **接口说明文档** | AI 有时不清楚接口形态时翻出来用 |
| **各类外部 API 调用文档** | 汇总整理 + AI 不清楚时作参考 |
| **架构设计文档** | 给新人 / 新 AI 看 |

**Lucoshin 的坦白**（§十五会再引用）：
> "但是说后面项目大了，上下文太长了，这些东西自己就懒得看了。"

### 3.6 Doc3 · PRD.md vs CURRENT.md（重要但容易被忽略）

```
docs/
├── PRD.md           // 产品宏观描述，最终形态
├── CURRENT.md       // 产品当前描述，现状
├── ARCHITECTURE.md  // 产品架构
└── API.md           // 当前项目 API 文档
```

**为什么要分两份**：
- PRD 是**未来**想做成什么样
- CURRENT 是**现在**实际做到了什么
- 很多项目把两者混在一个文档里——AI 读的时候分不清"已经有"和"期望有"，结果按 PRD 当作现状去写代码（新 bug 制造机）

## 四 · 可推理性（整个文档工程的底层判据）

### 4.1 定义（Doc1）

**可推理性** = 满足下面三件事：
- 看到一个**改动** → 能立刻知道应该更新哪类文档
- 看到一份**文档** → 能立刻知道它是规则、过程，还是成品
- 看到一个**目录** → 能立刻知道它服务的是谁

### 4.2 失去可推理性的 3 种翻车

| 误用 | 症状 |
|---|---|
| 规范写进成品文档 | 读者分不清"当前事实"和"编写要求" |
| 过程记录写进成品文档 | 正式文档越来越脏，可信度下降 |
| 成品示例写进规则文件 | 规则越来越重，维护成本越来越高 |

### 4.3 为什么这是**底层**判据

所有具体规则（目录怎么分、文件怎么命名、CLAUDE.md 写什么）都是**为了可推理性服务的**。

如果你不知道某个规则该怎么定 —— 就回到这三条判断："改动/文档/目录读了以后，我能立刻知道 XX 吗？"。

## 五 · 规则层次：全局 vs 项目

### 5.1 核心判词（Doc1）

> **"越靠上的规则，越应该抽象；越靠近项目的规则，越应该具体。"**

### 5.2 全局 `AGENTS.md` / `CLAUDE.md` 的 7 模块骨架（Doc1）

1. **身份与协作** — 角色定义、语言、基于事实判断
2. **工程决策原则** — 最小充分变更 / 可验证方案 / 显式说明取舍
3. **工具使用边界** — 优先安全读写、禁止绕过项目约束
4. **危险操作确认** — 删除/覆盖/批量改写/历史重写要先授权
5. **文档同步原则** — 涉及公开行为/核心规则/结构变更时必须检查
6. **输出与沟通** — 事实/推断/风险/建议分开
7. **规则优先级** — 项目级 > 全局级；具体 > 抽象

**全局级不写什么**：
- ❌ 操作系统（macOS、Windows）
- ❌ 包管理器（pnpm、yarn）
- ❌ 目录结构
- ❌ 框架版本
- ❌ 工具名

→ 否则一换项目/换环境就失效。

### 5.3 项目级 `AGENTS.md` 的 9 模块骨架（Doc1）

1. 项目事实来源（优先级：代码 > 项目规则 > 项目文档 > 全局规则；代码和文档不一致时以代码为准）
2. 项目目标与边界（主要职责 / 不做 / 对外暴露方式 / 核心依赖）
3. 分层与职责（Controller / Service / Repository / Model 的职责 + 禁止事项）
4. 编码与实现约束（现有风格 / 最小变更 / 新依赖要说明）
5. **文档同步矩阵**（哪些改动触发哪类文档更新 —— 见 §5.4）
6. 文档产物约定（接口文档放哪 / 业务文档放哪 / 任务文档放哪 / 命名规则）
7. 接口文档规范入口（不在本文件写详规，指向 `docs/API_DOC_STANDARD.md`）
8. 验证与交付标准（最低验证要求 / 交付完成定义）
9. 高风险操作补充（项目特有的高风险范围，如生产配置、迁移脚本、结算数据）

**项目级不承载**：
- ❌ 大段接口模板
- ❌ 冗长字段样板
- ❌ 模块业务细节全集
- ❌ 大量历史背景

### 5.4 文档同步矩阵（精华 · Doc1）

| 改动类型 | 必须检查更新的文档 |
|---|---|
| 修改公开路由 / 请求参数 DTO / 响应模型 / 返回码 / 鉴权方式 | 接口文档 |
| 修改核心业务规则 / 状态流转 / 校验逻辑 / 领域枚举 | 业务文档 |
| 修改系统架构 / 中间件 / 配置来源 / 外部依赖 / 部署方式 / 任务调度 | 技术文档 |
| 修改表结构 / 字段定义 / 索引 / Migration / 初始化数据 / 关键 SQL | 数据库文档 |

**原则**：若无需更新文档，**必须记录原因**（而不是默默不写）。

## 六 · 目录结构与边界问题

### 6.1 Doc1 的推荐骨架

```
AGENTS.md
.codex/
├── docs/
│   ├── WORKFLOW.md
│   ├── DOC_GOVERNANCE.md
│   ├── API_DOC_STANDARD.md
│   └── TASK_TEMPLATE.md
├── tasks/
│   ├── task-2026-03-11-xxx.md
│   └── task-2026-03-11-xxx.sql
└── templates/
    ├── api-doc-template.md
    └── task-template.md
doc/
├── api/
│   ├── order-api.md
│   ├── party-api.md
│   └── order-api.yaml
├── business/
└── architecture/
```

### 6.2 这不是目录问题，是边界问题（Doc1 原话）

- `AGENTS.md` = 项目入口、规则摘要、路径索引
- `.codex/` = Agent **执行层**（给 AI 看）
- `doc/` = 项目**交付层**（给人看）

对照：
- `.codex/docs/API_DOC_STANDARD.md` ≈ "Codex 如何生成接口文档"的规范
- `doc/api/order-api.md` ≈ "订单模块接口成品文档"

**边界划不清会发生什么**：
- 模板放进成品目录
- 任务记录放进正式文档
- 编写规则放进项目入口
- → 最后**看起来文档很多，实际上没一份好读、好用、好维护**

### 6.3 Doc3 的变体

```
README.md
AGENTS.md
.codex/
 - rules
docs/
 - requirements/
   - archive/
   - requirename-date/
     - require.md
     - test.md
 - PRD.md
 - CURRENT.md
 - ARCHITECTURE.md
 - API.md
```

和 Doc1 的共性：`.codex/`（给 AI） vs `docs/`（给人）；不同：Doc3 是"文档驱动"派，`requirements/` 下每个需求独立目录 + TDD 配套 `test.md`。

## 七 · CLAUDE.md 的正确姿势

### 7.1 定位（Doc4 · zhedream）

- **作摘要用**：不是"AI 的全局知识库"，而是"读者（AI 或人）快速了解项目注意事项"
- **自动触发**：Claude Code 读相关文件时，路径上有 CLAUDE.md 会自动加载
- 只写「怎么协作」：代码风格、禁改文件、验证流程

### 7.2 CLAUDE.md 的作用域（Doc4 · zhedream · 容易被忽略的点）

```
/CLAUDE.md              ← 全项目规范
/frontend/CLAUDE.md     ← 前端特有约定
/backend/CLAUDE.md      ← 后端特有约定
```

Claude Code 会**按路径自动加载**对应的 CLAUDE.md。所以不要把所有规则都堆根目录的一个文件里。

### 7.3 不写什么

- 操作系统 / 包管理器 / 框架版本（全局级就不该写；项目级可以但要节制）
- 业务细节（塞 `docs/business/`）
- 历史背景（塞 git log）
- 大段接口模板（塞 `docs/api/`）

### 7.4 适度长度

Doc1 没给具体数字，但从"高频入口尽量短"推——**实操经验 100 行以内** 是比较安全的。

超过 100 行的信号：
- 打开就要滚动才能看完 —— 下次你 / AI 就懒得读
- 涉及多个具体业务细节 —— 该往下沉到 `docs/`

## 八 · Token 哲学（全篇最被忽视但最实用的一条）

### 8.1 核心判词（Doc1）

> **"真正节省 token 的方法不是 '少写文档'，而是：**
> - **高频入口尽量短**
> - **细则按层外置**
> - **只在命中时按需读取。"**

### 8.2 反直觉点

很多人以为省 token = 少写文档。错了。

少写文档 → AI 没东西读 → 写代码靠瞎猜 → 结果更糟、反复对话的 token 消耗更大。

正确做法：
- 入口短（`CLAUDE.md` / `AGENTS.md` 100 行内）
- 细则不在入口里，**但要存在**且**能被 AI 找到**（清晰的目录 + 命名）
- AI 读入口时知道"哦需要业务规则 → 去 `docs/business/` 找"，按需加载

### 8.3 AI 不看长文档（Doc4 · zhedream）

> "当然不是说文档彻底不用，但 AI 基本不会去看的，看了也是浪费上下文。一般是我主动投喂的。"

要 AI **真读**，只有两条路：
1. 写短到 `CLAUDE.md` 就能触发
2. **人主动投喂**（@ 文件、贴路径、`Read` 指令）

"写长文档然后期待 AI 自己翻"是一种自我感动。

## 九 · 迁移策略（旧项目接入文档工程时）

### 9.1 历史文档的 3 种状态（Doc1）

- 已经过时
- 仍然部分有效
- 仍然是当前唯一可信来源

### 9.2 最危险的动作（Doc1）

**"急着全部迁移"** —— 不区分这三种状态就直接迁，会把**历史问题整体复制到新体系**。

### 9.3 稳妥策略（Doc1）

1. 先建立新的文档工程骨架
2. 明确旧文档是**历史参考**
3. 在真实需求命中时，**逐步迁移**仍有价值的内容

## 十 · 初建策略 / 健康判据

### 10.1 初建只要骨架（Doc1）

**不要被"看起来不完整"绑架**。

骨架需要且只需要 5 件事：
- 入口（`CLAUDE.md` / `AGENTS.md`）
- 分层（规范 / 过程 / 成品）
- 落点（每类文档放哪个目录）
- 模板（至少 1 份任务档模板 + 1 份接口档模板）
- 触发规则（文档同步矩阵）

**硬塞一堆"看起来完整"的模板 → 最后产生"看起来完整，实际没人用"的空壳文档**。

### 10.2 健康判据（Doc1 · 6 条）

判断文档工程健不健康，看下面 6 件事（**不是看文档多不多**）：

1. 新任务来了，是否知道该往哪里记？
2. 接口改了，是否知道该更新哪里？
3. 业务规则变了，是否知道落到哪一层？
4. 历史文档和新文档边界是否清楚？
5. 高频入口是否仍然短而可用？
6. AI 在不额外解释很多的情况下，是否已经能找到基本落点和规则入口？

这 6 条大多数都能回答 → 文档工程即使稀疏也是**有效的**。

### 11.3 YMuxing 的"一次性再生成"策略（反常识 · 值得单独提炼）

工作时**不产出长文档** → 项目做完 → 开新对话让 AI 索引整个项目 → **一次性生成** 2 份文档（架构 + README）。

**优点**：AI 在有完整项目现状时生成的文档 > AI 在项目进行中每步产出的碎片文档
**缺点**：中途新人接手没法立刻读
**适用**：小团队短周期项目

### 12.1 joyousoda 原话

- → **过程文档 = 你的免责证据**

- Bug 踩坑记录（下次再踩 AI 先查）

- 代码规范（团队协作统一）

## 十三 · Skill 与工具链

### 13.1 Codex-Doc-Workflow（Doc1 附录）

作者 joyousoda 给了完整 YAML。核心是 **4 命令**：

| 命令 | 作用 |
|---|---|
| `$init-task` | 初始化任务文档（手动或 `--auto` 自动扫仓库） |
| `$sync` | 增量同步进度 + 实现记录 |
| `$finalize-impact` | 回填影响范围 / 代码定位（`path:line` 格式） / 数据库变更 / Mermaid 流程图 |
| `$wrap-up` | 结项校验 / 运行构建 / 回写验证记录 / 生成 commit message |

**关键约束**：
- 文件定位统一 `FileName:LineNumber` 或 `path/to/file:line`
- 后端且涉及数据库：必须补"数据库变更记录"；未涉及 DB **也必须显式写"无数据库变更"**
- Mermaid 流程图默认 `flowchart TD`；多角色交互用 `sequenceDiagram`；节点控制 5-10 个

### 13.2 OpenSpec + Codex CLI（Doc3）

- OpenSpec：把"一句话需求"拆成 4 文档（`proposal` / `specs` / `design` / `tasks`）
- Codex CLI 优势：并发工作（开多个终端）、直接执行命令可见、生态丰富
- 配套 Skills 包：github.com/ikunycj/docscode

### 13.3 TDD 结合（Doc3）

红 → 绿 → 重构：
1. **红**：写一个必将失败的测试用例
2. **绿**：写最少量代码让测试通过
3. **重构**：在测试保护下优化代码，功能不变

需求文档生成时**同时产出 `test.md`**，AI 全流程携带两份构成闭环。

### 13.4 mcp-memory-service（Doc5 #7 · Lucoshin 提到）

- github.com/doobidoo/mcp-memory-service
- 用途：AI agent pipelines（LangGraph / CrewAI / AutoGen / Claude）的持久记忆
- 组件：REST API + knowledge graph + autonomous consolidation
- **没展开用过**，标为"待调研"

## 十五 · 轻派诚实承认层

轻派不是"不要文档"，是"不要屎山"。放这里和重派**并列**不是对立。

### 15.1 核心主张（Doc4 · zhedream）

## 十七 · 小红书第一条可用角度

> 这些是候选，由用户最终拍板。

### 角度 A · 10 条规则干货合集 · **首选**
把 5 派精华融成 10 条，每条 100-150 字，1200-1500 字干货满满。核心是让读者**看完就想收藏**。
- 优点：密度高、信息量大、可收藏
- 风险：规则列表容易踩 §3.2 第 5 条（整齐 N 要点）—— 用**段落长度不均** + **具体文件名** + **自嘲** 破相
- 具体规则清单见 §十七.1

### 角度 B · 可推理性单概念深挖
只讲 §四 一件事：看到改动立刻知道该更新哪份文档。
- 优点：立意高、有壁垒、不易 AI 化
- 风险：读者需要一定工程基础；流量面较窄
- 适合：即刻 / 公众号 > 小红书

### 角度 C · Token 哲学单点深挖
只讲 §八。"真正省 token 的不是少写文档，是入口短。"
- 优点：对 Claude Code 重度用户强打击（Max 用户都在抱怨 token）
- 风险：受众窄；小红书上 Cursor/Claude 用户虽在涨但还不是主流
- 适合：次优选

### 角度 D · 过程文档的"维权"用途
只讲 §十二。切入点奇特 —— 文档不只是给 AI 读，还是你和领导对线的证据链。
- 优点：钩子强、有故事、角度独特（完全没其他 AI 会挑这个）
- 风险：受众是企业内打工人，不是独立开发者（和账号定位偏离）
- 适合：冷启动不建议；后期做"打工人 AI 协作"系列可用

### 角度 E · "在项目里拉屎"故事向
从 clenlu 金句切入，讲自己用 AI 写代码被"屎山淹没"的经历 + 收敛到 10 条规则。
- 优点：钩子黄暴有记忆点
- 风险：标题过重、账号冷启选这个调性有风险
- 适合：后期风格确定后的专题

**结论**：第一条强烈推荐 **角度 A**；如果要一个备选就 **角度 E**（戏剧化版本）。

### 十七.1 · 10 条规则清单（角度 A 的骨架）

1. **可推理性**：看改动知道更新哪份文档（§四）
2. **三层分离**：规范 / 过程 / 成品（§3.1）
3. **4 分类上 Git**：判断题"半年后还有人读吗"（§3.2）
4. **给 AI 看 vs 给人看，物理分离**：`.codex/` + `docs/`（§6.2）
5. **CLAUDE.md 100 行 + 分作用域**（§7）
6. **真正省 token 的不是少写，是入口短**（§八）
7. **PRD.md vs CURRENT.md 要分开**（§3.6）—— 未来 vs 现在
8. **模板从真实产出里抽，别凭空设计**（§A4）
9. **DEBUGGING.md 是下次省时间的**（§12 + §3.5）—— 踩坑手册 > 长文档
10. **AI 不看长文档**（§8.3）—— 要它读只有两条路：短到入口就触发 / 人主动投喂
