# 文档工程 · AI 协作的重派与轻派

> 来自 linux.do 四个同主题帖子的合并沉淀。最高价值不在任一派的方法论本身，而在重派 vs 轻派的立场张力——以及这个张力在**前端 vibe coder 视角下几乎没人填过**的空白。

---

## 一、一句话带走

**重派**说"文档工程不是为了制造更多文件，它是为了让知识具备结构、边界、演进路径和可追溯性"。
**轻派**说"代码 > 注释 > CLAUDE.md > 文档，长文档 AI 根本不会看，看了也是浪费上下文"。
两派各自成立——取决于**项目阶段 × 团队规模 × 代码稳定性**。

---

## 二、重派主张（Doc1 @joyousoda · 31 赞原创方法论）

### 问题诊断
项目文档常走两个极端：一极是"没有文档，知识全在代码和脑子里"；另一极是"建了很多文档但只是静态堆积，没有职责，没有演进机制"。AI 辅助开发会**放大**这个问题——AI 没边界就开始"模仿着写"，看起来像那么回事，悄悄给你带两个 bug。

### 解决方案：三层分离
| 层 | 回答的问题 | 读者 |
|---|---|---|
| 规范层 | 文档怎么写、目录怎么分、哪些改动触发哪些文档更新 | 团队 + AI |
| 过程层 | 这次任务做了什么、影响哪些模块、做过哪些验证 | 开发执行 + 追溯 |
| 成品层 | 系统当前对外暴露什么、模块接口/业务规则/架构边界是什么 | 所有人（稳定、可读）|

三层混在一起会失去"**可推理性**"——看到改动无法立刻知道该更新哪类文档。

### 全局 AGENTS.md：越靠上越抽象
> "越靠上的规则，越应该抽象；越靠近项目的规则，越应该具体。"

全局只回答"怎么协作"，不回答"某个项目具体长什么样"。**不写操作系统、包管理器、框架版本、工具名**。否则一换环境就失效。

七个模块：
1. 身份与协作
2. 工程决策原则（最小充分变更、可验证方案、显式说明取舍）
3. 工具使用边界
4. 危险操作确认（删除/覆盖/批量改写/历史重写要显式授权）
5. 文档同步原则（涉及公开行为/核心规则/系统结构时检查同步）
6. 输出与沟通（事实/推断/风险/建议分开）
7. 规则优先级（项目级 > 全局级；具体 > 抽象）

### 项目级 AGENTS.md：短而硬
九个模块：项目事实来源 / 目标与边界 / 分层职责 / 编码约束 / **文档同步矩阵**（哪些改动要更新哪类文档）/ 文档产物约定（路径）/ 接口文档规范入口 / 验证与交付标准 / 高风险操作。

**不承载**：大段接口模板、冗长字段样板、模块业务细节全集、大量历史背景。

> "真正节省 token 的方法不是'少写文档'，而是：高频入口尽量短，细则按层外置，只在命中时按需读取。"

### 目录约定
```
AGENTS.md
.codex/
├── docs/        # WORKFLOW / DOC_GOVERNANCE / API_DOC_STANDARD / TASK_TEMPLATE
├── tasks/       # task-YYYY-MM-DD-*.md
└── templates/
doc/
├── api/
├── business/
└── architecture/
```
- `.codex/` = Agent 执行层（给 AI 看的工作流、模板、任务档）
- `doc/` = 项目交付层（给人看的成品）
- **这看起来是目录问题，实际是边界问题**。边界划不清，模板会混进成品目录，任务记录会混进正式文档。

### 四条关键判断原则
1. **模板要从成品里提炼**，不能凭空设计。"让模板来自真实生产，而不是来自想象中的完美结构。"
2. **历史文档不要急着全迁移**。已过时 / 仍部分有效 / 仍是唯一可信来源——三类不区分就迁，会把历史问题整体复制到新体系。
3. **初建阶段只要骨架**（有入口/分层/落点/模板/触发规则）。**"结构先成立，内容后生长。"** 一开始就补齐所有业务/架构/任务/模板，大概率产出"看起来完整，实际没人用"的空壳。
4. **健康判据**（不是看文档多不多）：新任务知道该记哪里？接口改了知道更新哪里？高频入口是否仍然短？AI 是否在不额外解释的情况下能找到落点？

### 配套 Skill：Codex-Doc-Workflow
joyousoda 同时给了一份 YAML 格式的 Skill 定义（v1.6.0），4 个命令：
- `$init-task`：初始化任务文档（支持 `--auto` 自动扫仓库模式）
- `$sync`：增量同步进度和实现记录
- `$finalize-impact`：回填影响范围、代码定位（path:line 格式）、数据库变更、Mermaid 流程图
- `$wrap-up`：结项校验、运行构建、回写验证记录、生成 commit message

## 三、轻派主张（Doc4 #14 @zhedream · 2 赞但观点犀利）

> 好的代码是不需要注释的，代码即注释。
> 好的代码是不需要文档的，代码即文档。
> 文档多了也是屎山。最后用也不会用。
> **代码 > 注释 > CLAUDE.md（摘要与注意事项）> 文档**

实操三条：
1. **能不写文档就不写**，CLAUDE.md 当摘要特别好使，Claude 每次读取相关文件会自动加载路径下的 CLAUDE.md
2. **AI 基本不会去看长文档，看了也是浪费上下文**——要投喂是人主动投喂
3. **CLAUDE.md 有作用域**——根据需要分散写到不同目录的 CLAUDE.md，不是全堆到根目录的一个

### Doc4 楼主的真实痛点
@z1056544889 起初只分两类（正式→`docs/`，讨论评审→`discuss/`），觉得粒度太粗。这个痛点是普遍的——**重派和轻派都在回答同一个问题**。

### Doc4 其他有意思的答案
- @ogas：统一到 `./.codex/` 或 `./.claude/`
- @Pleasure1234：挑有意义的导出到 Obsidian（**注意：这是你可能会走的路**）
- @gadfly3173：有用的留，没用的（"本次修复了什么什么"）就删
- @YMuxing：产出文档全删，最后让 AI 重新索引整个项目生成 2 个文档（一个架构 + 一个 README）
- @clenlu："多人协作让 AI 总结下项目就好了，那么多文档也没人愿意看，而且还像是在项目里拉屎"——纯轻派立场

## 四、中间派补充

### Doc2 @joyousoda 的二次分类（同 Doc1 作者）
| 类别 | 是否上 Git |
|---|---|
| 1. 工作流框架生成的运行过程文档 | 不上 |
| 2. **成品文档**（业务 / 接口 / 需求）| 上 |
| 3. 与 AI 头脑风暴的前期文档 | 不上 |
| 4. **代码规范 + bug 踩坑记录** | 上 |

> "最终需要关注的是成品文档，不仅是人可以看，也作为 AI 在新需求和修改需求的知识库。另外过程文档 AI 也是可以检索的（相信 AI），我平常让他翻出来和领导对线当时是谁让我改的：包括 git 记录、issue 记录。"

### Doc3 @1870884413 · 文档驱动开发 + TDD（14 赞）
- 核心立场：**"Markdown 是 AI 时代的源代码"**——编程的重点从"写代码"转到"写需求文档"
- 工具栈：**OpenSpec**（Fission-AI/OpenSpec）把"一句话需求"拆成四文档：`proposal`（为什么做）/ `specs`（需求和场景）/ `design`（技术设计）/ `tasks`（实施清单）+ **Codex CLI** 作为落地入口
- 目录设计：
  ```
  docs/requirements/
  ├── <需求名-日期>/
  │   ├── require.md
  │   └── test.md
  └── archive/
  docs/
  ├── PRD.md          # 产品宏观描述
  ├── CURRENT.md      # 产品当前现状
  ├── ARCHITECTURE.md
  └── API.md
  ```
- 与 TDD 结合：生成精细需求文档的同时产出 test 文档，AI 全流程携带这两份构成闭环

### 其他零散做法
- **按日期分文件夹**（Doc2 @user231）：`20260414/01-xxx.md`，简单但有效
- **会话文档管理方式**（Doc2 @xx_yy1）：没细说，但暗示有一整套流派围绕"AI 对话即文档源"

## 六、对你（作为前端 vibe coder + OPC）真正有用的角度

> 这些不是我已经挑定的角度，是候选——等你从"可用角度"里选或自己加新的。

### 角度 A · 写一篇"AI 协作文档：重派还是轻派？"
直接把张力抛出来。你不需要是方法论权威，只需要呈现争议并给出**你的判断标准**（项目阶段 / 团队规模 / 代码稳定性哪个维度决定）。
适配：小红书卡片 / 即刻短思考 / Linux.do 深度

### 角度 B · "前端项目的 AGENTS.md 该怎么写？"
所有样例都是后端 Java，你可以填这个空白——用 Next.js + Shadcn/ui 项目做一份前端版 AGENTS.md。**这是 build in public 小工具天然的附加产物**（等 Month 3-4 启动第一个 build in public 时自然就有材料）。

### 角度 C · 反推迟视角
把 joyousoda 的"结构先成立，内容后生长"和 **"初建阶段不该被'看起来不完整'绑架"** 拿出来——这正是对你自己推迟模式的一面镜子。主题："我为什么决定先发第一条，再回头补文档工程。"
**适配度最高**——和你自己 4/24 硬约束强相关，有真实处境做锚。

### 角度 D · "一个 CLAUDE.md 摘要 vs 一整套文档工程：vibe coder 该选哪个？"
把 zhedream 的"AI 不看长文档"和 joyousoda 的"三层分离"放在一起对比——这是很强的阅读钩子（二选一）。可以给出自己的经验判断。

### 角度 E · 拆出 OpenSpec / Harness Engineering 单独做素材
Doc3 提到的 OpenSpec 和 Doc1 #9/#17/#19 提到的 **Harness Engineering（OAI 方法论）** 都值得单独挖（见"盲点"）。
