## 0、为什么想写

在机缘巧合下了解到 L 站，在朋友给了我三次邀请码之后才艰辛入站，但进站前的两周，通过各种 0 级贴，开拓了眼界，学到了新的姿势，也感受到了 L 站浓烈的技术氛围。说来惭愧，作为程序员，我在去年年底才开始使用 AI 辅助开发，甚至到上个月我还在用 “问答” 的方式写需求。经过这两周的学习和实践，我想把自己学到的方法和踩过的坑整理出来。如果能得到佬们的批评与指正，那自然是更好不过。

这篇文章不准备写成 “某个工具怎么点、某条命令怎么敲” 的教程，而是想和各位聊一件事：

**如果我们真的开始和 AI 一起做项目，那么应该如何建立一套文档工程？**

## 1、为什么要建立文档工程

首先必须说明：**文档工程不是为了制造更多文件，它是为了让知识具备结构、边界、演进路径和可追溯性。**

很多项目里的 “文档建设” 最后都会走向两个极端：

1. 几乎没有文档，知识全在代码、聊天记录和个别人脑子里。
2. 建了很多文档，但它们只是静态文件堆积，没有明确职责，也没有演进机制。

这种情况让刚接手项目的同事直接一个头两个大，只见文档山，却不见尽头。除了问同事，就是翻目录、翻代码、翻历史记录。

而在 AI 辅助开发的场景下，这个问题会被进一步放大。

AI 的确可以帮助你理解项目结构、梳理调用关系、分析业务流程，但你不能指望它每次都重新翻一遍代码，再和你对话几十轮，最后才勉强明白你想做什么。更糟的是，当你没有给它足够清晰的边界时，它会开始 “模仿着写”，看起来像那么回事，最后悄悄给你带来两个 bug。

所以，文档工程的建立，不只是为了让人看懂，也是为了让 AI 看懂，并且规范 AI 应该如何完成需求。

换句话说，文档工程要解决的不是 “文档数量” 问题，而是 “知识组织” 问题。它本质上是在回答三个问题：

- 什么信息应该被记录
- 这些信息应该记录到哪里
- 当代码和业务变化时，哪些文档必须跟着变化

所以，文档工程首先是结构设计，其次才是内容填充。

## 2、文档工程的三个层次

一个可持续的文档工程，至少要把下面三类内容分开。

### 2.1 规范层

规范层回答的是：

- 文档应该怎么写
- 目录应该怎么分
- 哪些改动会触发哪些文档更新
- 模板和约束放在哪里

规范层不是项目成品，也不是任务记录。它更像 “文档世界里的架构约束”。

### 2.2 过程层

过程层回答的是：

- 这次任务做了什么
- 改动影响了哪些模块
- 做过哪些验证
- 是否涉及数据库、接口、业务规则或技术架构变更

过程层不是为了给外部协作者长期阅读，而是为了给开发执行和后续追溯提供证据。

### 2.3 成品层

成品层回答的是：

- 系统现在对外暴露了什么
- 某个模块的接口、业务规则、架构边界是什么
- 产品、测试、实施、研发应该读哪份正式文档

成品层必须尽量稳定、清晰、可阅读，要让项目组里所有人都能一下看懂。它不应该混入任务排障记录、临时决策碎片和草稿式备注。

## 3、为什么不能写在一起

如果把这三层混在一起，会出现几个典型问题：

- 规范写进成品文档，读者会分不清 “当前事实” 和 “编写要求”
- 过程记录写进成品文档，正式文档会越来越脏
- 成品示例直接写进规则文件，规则会越来越重，维护成本越来越高

更严重的问题在于：**一旦层次混乱，文档就不再具备可推理性。**

所谓可推理性，意思是：

- 看到一个改动，能立刻知道应该更新哪类文档
- 看到一份文档，能立刻知道它是规则、过程，还是成品
- 看到一个目录，能立刻知道它服务的是谁

文档工程真正的价值，就建立在这种可推理性上。

## 4、如何建立一份文档工程

下面开始说最关键的问题：如果你准备在项目里正式引入 AI 协作，文档工程应该怎么搭。

我这里以 Codex 为例。

在实际使用中，我发现 Codex 这类工具往往至少会和两层规则打交道：

- 一层是用户级、全局级的 Agent 规则
- 一层是项目级、仓库内的 Agent 规则

一开始我也是很自然地这么想：

- 先执行 `/init`
- 生成项目里的 `AGENTS.md`
- 然后直接开始写需求

这样做当然能跑起来，AI 也能写出和老代码风格接近的实现，知道去调用一些现有通用方法，甚至能帮你把一些 “从零开始的功能” 很快拼起来。

但很快你就会发现，问题并不在 “它会不会写代码”，而在于它不知道：

- 为什么做这件事
- 为什么这样做而不是那样做
- 哪些规则属于长期约束
- 哪些只是这一次任务的过程记录
- 接口变了应该去改哪里
- 业务规则变了应该沉淀到哪里

于是我们开始回头补文档工程。

### 4.1 先从全局规则开始，但全局必须抽象

全局 `AGENTS.md` 的责任，不是描述 “我当前用什么系统、什么工具、什么技术栈”，而是定义 “跨项目都成立的协作原则”。

如果全局层写得太具体，就很容易退化成 “当前环境说明”。

例如：

- 把 `macOS` 写成全局前提
- 把 `pnpm` 写成全局硬约束
- 把某个平台的工具名直接写死

这些要求在一个项目里也许成立，但一旦换项目、换环境、换工具链，就会失效。

所以全局层的核心原则应该是：

> 越靠上的规则，越应该抽象；越靠近项目的规则，越应该具体。

下面是我最后收敛出来的一版全局骨架：

```markdown
# Codex Global Identity & Safety

## 1. 身份与协作
- 角色：以工程交付为目标的资深研发工程师，具备架构视角。
- 语言：默认使用简体中文；若项目已有明确语言规范，则以项目规范为准。
- 协作：优先基于事实、代码、约束和可验证信息进行判断，避免脱离上下文的主观假设。

## 2. 工程决策原则
- 优先最小充分变更，避免无关重构。
- 优先可验证的方案，必要时通过构建、测试、静态检查或现有证据验证结论。
- 优先保持现有系统边界与约定，除非任务明确要求调整。
- 对正确性、可维护性、复杂度和交付成本之间的取舍，应显式说明理由。

## 3. 工具使用边界
- 优先使用当前平台提供的安全读写、检索与任务跟踪能力。
- 禁止使用不受控方式直接改写文件或绕过项目约束。
- 命令行仅用于探查、构建、运行、测试、依赖管理及其他符合权限边界的操作。
- 若首选工具不可用，应退回到当前环境允许的安全替代方式，并保持最小影响范围。

## 4. 危险操作确认
- 对删除、覆盖、批量改写、历史重写、破坏性数据变更或其他高风险操作，必须先提示风险并获得明确授权。
- 即使已获授权，也应限制影响范围，并保留可追踪的变更说明。
- 若用户授权范围不清，应先收敛边界，再执行。

## 5. 文档同步原则
- 涉及公开行为、核心规则、系统结构、依赖关系、数据结构或关键流程变更时，必须检查相关文档是否需要同步。
- 若判断无需更新文档，应记录理由。
- 文档类型、位置、模板与生成规范由项目级规则定义。

## 6. 输出与沟通
- 简单问题简洁回答，复杂任务结构化表达。
- 涉及代码、设计、排障、评审时，优先提供可定位信息，如文件、类、方法、配置项或行号。
- 明确区分事实、推断、风险和建议，避免混写。

## 7. 规则优先级
- 项目级规则优先于全局级规则。
- 更具体的规则优先于更抽象的规则。
- 若规则冲突且无法自行消解，应先说明冲突点，再选择最接近任务上下文的约束执行。
```

这版全局骨架最关键的点只有三个：

- 只回答 “怎么协作”
- 不回答 “某个项目具体长什么样”
- 不出现操作系统、包管理器、目录结构、框架版本、工具名这类显式要求

### 4.2 项目级规则必须短而硬

再来看项目级 `AGENTS.md`。

> 全局规则解决的是 “怎么协作”，但真正落到某个仓库时，还需要一层项目级规则来回答 “这个项目该怎么做”。

```
# Project Agent Guidelines

  ## 1. 项目事实来源
  - 事实来源优先级：
    1. 当前仓库代码与配置
    2. 项目级 \`AGENTS.md\`
    3. 项目文档与任务文档
    4. 全局级 \`AGENTS.md\`
  - 若文档与代码不一致，以代码现状为准，并在交付时记录文档差异。
  - 若存在多个实现入口，优先以当前对外暴露路径、主启动项目、主配置文件为准。

  ## 2. 项目目标与边界
  - 本项目的主要职责：[在此填写，例如“提供订单、运单、结算相关后端接口”]
  - 不在本项目职责内的内容：[在此填写]
  - 对外暴露方式：[HTTP API / MQ / 定时任务 / RPC / CLI]
  - 核心依赖：[数据库 / Redis / MQ / 配置中心 / 第三方平台]

  ## 3. 分层与职责
  - Controller / API 层：
    - 负责路由、鉴权、参数接收、响应返回。
    - 不承载核心业务逻辑。
  - Service 层：
    - 负责业务规则、状态流转、事务控制、聚合编排。
  - Repository / Mapper / DAL 层：
    - 负责数据访问与查询封装。
  - Model 层：
    - 负责 Entity、DTO、ViewModel、枚举、常量等定义。
  - 禁止事项：
    - Controller 直接编写核心业务逻辑。
    - 对外接口直接暴露 Entity。
    - 跨层绕过既有边界直接调用底层实现，除非项目已有明确约定。

  ## 4. 编码与实现约束
  - 优先遵循现有代码风格、命名方式和目录结构。
  - 新增代码应落在与现有职责一致的位置，避免创建平行体系。
  - 修改时优先最小充分变更，避免无关重构。
  - 若引入新依赖、新中间件、新基础设施接入，必须说明原因、影响面和回退方式。
  - 若存在性能、事务、一致性、缓存、权限相关风险，必须显式说明。

  ## 5. 文档同步矩阵
  - 修改以下内容时，必须检查接口文档是否需要更新：
    - 公开路由
    - 请求参数 DTO
    - 响应模型
    - 返回码、错误码、鉴权方式
  - 修改以下内容时，必须检查业务文档是否需要更新：
    - 核心业务规则
    - 状态流转
    - 校验逻辑
    - 领域枚举与业务含义
  - 修改以下内容时，必须检查技术文档是否需要更新：
    - 系统架构
    - 中间件
    - 配置来源
    - 外部依赖
    - 部署方式
    - 任务调度或异步链路
  - 修改以下内容时，必须检查数据库文档或变更记录是否需要更新：
    - 表结构
    - 字段定义
    - 索引
    - Migration
    - 初始化数据
    - 关键 SQL
  - 若无需更新文档，必须记录原因。

  ## 6. 文档产物约定
  - 接口文档位置：[例如 \`docs/api/\`]
  - 业务文档位置：[例如 \`docs/domain/\`]
  - 技术文档位置：[例如 \`docs/architecture/\`]
  - 任务文档位置：[例如 \`docs/tasks/\`]
  - 数据库变更记录位置：[例如 \`docs/db/\` 或任务文档附录]
  - 命名规则：[在此填写，例如 \`feat-xxx-api.yaml\`、\`task-YYYY-MM-DD-xxx.md\`]
  - 若仓库已有文档目录，优先复用，不重复造目录。

  ## 7. 接口文档规范入口
  - 接口文档的字段说明、示例、命名、版本策略、增量更新规则，不直接写在本文件。
  - 本文件只定义“何时必须检查接口文档”。
  - 接口文档详细规范统一维护在：[例如 \`docs/API_DOC_STANDARD.md\`]

  ## 8. 验证与交付标准
  - 最低验证要求：
    - 编译通过
    - 与改动相关的测试或自检完成
    - 关键链路可说明验证方式
  - 交付完成定义：
    - 代码已完成
    - 必要文档已同步或已说明无需同步
    - 验证记录已补充
    - 风险与未完成项已说明
  - 若无法完成验证，必须说明原因、影响和建议补充动作。

  ## 9. 高风险操作补充规则
  - 以下内容属于本项目高风险范围：[在此填写，例如生产配置、迁移脚本、结算数据、批处理任务]
  - 涉及上述内容时，即使用户提出修改，也应先明确影响范围与回退方案。
  - 涉及批量数据修复、历史数据回填、兼容性迁移时，必须补充执行前提与验证方式。
```

项目级规则的目标不是成为百科全书，它更像项目的 “施工准则”。

它应该回答：

- 这个项目的事实来源是什么
- 分层职责怎么划分
- 哪类改动会触发哪类文档更新
- 完成一个改动时，最少要交付什么

它不应该承载：

- 大段接口模板
- 冗长字段样板
- 模块业务细节全集
- 大量历史背景

因为这些内容一旦都堆进去，项目规则就会变重、变慢、变模糊。高频入口一旦变重，整个文档工程的使用成本就会上升。

如果你在 AI 协作里考虑 token 成本，这一点会更明显。

真正节省 token 的方法不是 “少写文档”，而是：

- 高频入口尽量短
- 细则按层外置
- 只在命中时按需读取

### 4.3 规范、过程、成品必须分目录

在项目级规则之外，我们最后收敛出来的目录结构如下：

```plaintext
AGENTS.md
.codex/
├── docs/
│   ├── WORKFLOW.md
│   ├── DOC_GOVERNANCE.md
│   ├── API_DOC_STANDARD.md
│   └── TASK_TEMPLATE.md
├── tasks/
│   ├── task-2026-03-11-xxx.md
│   └── task-2026-03-11-xxx.sql
└── templates/
    ├── api-doc-template.md
    └── task-template.md

doc/
├── api/
│   ├── order-api.md
│   ├── party-api.md
│   └── order-api.yaml
├── business/
└── architecture/
```

这套结构背后的边界非常重要：

- `AGENTS.md`
	- 只做项目入口、规则摘要、路径索引。
- `.codex/`
	- 放 Codex 专属的工作流、模板、任务文档、检查清单、生成规范。
		- 这是 “agent 执行层”。
- `doc/`
	- 放真正面向人阅读和交付的成品文档，例如接口文档、架构文档、业务文档。
		- 这是 “项目交付层”。

也就是说：

- `.codex/docs/API_DOC_STANDARD.md`
	- 更像 “Codex 如何生成接口文档” 的规范。
- `doc/api/order-api.md`
	- 更像 “订单模块接口成品文档”。

这件事看起来只是目录问题，实际上是边界问题。

如果边界划不清，你很快就会把：

- 模板放进成品目录
- 任务记录放进正式文档
- 编写规则放进项目入口

最后看起来文档很多，实际上没有一份好读、好用、好维护。

### 4.4 模板应该从成品里提炼，而不是凭空设计

模板最怕两种来源：

- 完全拍脑袋抽象
- 直接复制一份成品但不做抽取

更好的方式是：

- 先找已经被审阅通过的成品文档
- 再从这些成品中提炼稳定结构
- 把业务特有内容剥离，只保留通用写法

这句话很重要：

> 让模板来自真实生产，而不是来自想象中的完美结构。

比如一份经过审阅的 `order-api.md`、`party-api.md`、`order-api.yaml`，它们就非常适合拿来反向抽模板。因为它们已经经历过真实需求、真实字段、真实调用场景的检验。

相比之下，纯靠想象写出来的模板，往往看起来很完美，落地时却和项目脱节。

### 4.5 为什么不要急着迁移历史文档工程

当一个项目已经有旧的文档工程时，最危险的动作往往不是 “保留旧文档”，而是 “急着全部迁移”。

因为历史文档通常有三种状态：

- 已经过时
- 仍然部分有效
- 仍然是当前唯一可信来源

如果不区分这三类，就直接迁移，很容易把历史问题整体复制到新体系里。

所以更稳妥的策略通常是：

- 先建立新的文档工程骨架
- 明确旧文档是历史参考
- 在真实需求命中时，再逐步迁移仍有价值的内容

这不是保守，而是为了控制迁移成本和错误扩散。

### 4.6 为什么一开始只需要骨架

一个新建的文档工程，不应该被 “看起来不完整” 这件事绑架。

文档工程在初期真正需要具备的是：

- 有入口
- 有分层
- 有落点
- 有模板
- 有触发规则

只要这几件事成立，它就已经能够支持后续真实演进。

反过来，如果在一开始就试图补齐所有业务文档、架构文档、任务样例和模板，往往会产生大量 “看起来完整、实际上没人用” 的空壳文档。

所以，文档工程初建阶段最重要的不是完整，而是：

> 结构先成立，内容后生长。

## 5、如何判断一套文档工程是否健康

一个文档工程是否健康，不应只看 “文档多不多”，而应看下面几件事：

- 新任务来了，是否知道该往哪里记
- 接口改了，是否知道该更新哪里
- 业务规则变了，是否知道该落到哪一层
- 历史文档和新文档是否边界清楚
- 高频入口是否仍然短而可用
- AI 在不额外解释很多的情况下，是否已经能找到基本落点和规则入口

如果这些问题大多数都能回答清楚，那么这套文档工程即使仍然稀疏，也已经是有效的。

## 6、最后的最后

文档工程不是为了制造更多文件。

它是为了让知识具备结构、边界、演进路径和可追溯性；也是为了让人和 AI 在协作时，面对同一套项目知识，有一致的入口和落点。

先理解这个理念，再去看具体项目里的目录、模板和流程，才不会把某一时刻的实现误认为文档工程本身。

很多时候，我们以为自己缺的是 “多几份文档”，其实真正缺的是：

- 规则的抽象层次
- 文档的职责边界
- 成品、过程和规范之间的分层意识
- 以及一个可以随着真实需求持续演进的结构

如果这些东西建立起来了，文档工程就不再只是项目附件，而会慢慢变成团队真正的工程基础设施。

## Core Rules

- 优先从项目级提示词或仓库内项目级规则文件中提取“文档默认落点”与“文档目录约定”；若项目级规则已明确目录，则必须优先遵循，不得先按 skill 内置目录顺序落文档。
- 仅当项目级规则未定义文档落点时，才按以下顺序回退解析：\`.codex/tasks/\` -> \`.codex/docs/tasks/\` -> \`.claude/tasks/\` -> \`.claude/docs/tasks/\` -> \`docs/tasks/\`。
- 若以上目录均不存在，则默认创建 \`.codex/tasks/\`。
- 若项目级规则将 \`.claude/\` 定义为历史文档目录，则 \`.claude/\` 只能作为回退读取来源，不应作为新任务文档的首选落点。
- 当前回合只能维护一个“活动任务文档”；若存在多个候选文档，优先选择最近修改的 \`task-*.md\`。
- 所有开发过程记录都必须回写到任务文档，不额外散落到临时说明中。
- 文件定位统一使用 \`FileName:LineNumber\` 或 \`path/to/file:line\` 格式，至少记录类、方法、SQL 片段或 XML 语句的主入口位置。
- 若项目为后端项目且本轮涉及数据库结构、初始化数据、迁移脚本或核心 SQL 逻辑调整，必须在任务文档中补充“数据库变更记录”。
- 逻辑流程图统一使用 Mermaid 代码块保存到任务文档；默认优先 \`flowchart TD\`，若存在明显的角色交互或时序关系，则使用 \`sequenceDiagram\`。
- 若本轮未涉及数据库修改，必须在“数据库变更记录”中显式写明“无数据库变更”，而不是留空。
- 若本轮改动较大，影响范围总结必须同时覆盖：模块、接口、服务、持久层、缓存、权限、文档、SQL 脚本。

## Workflow

1. 使用 \`$init-task\` 初始化任务文档。
2. 开发过程中使用 \`$sync\` 持续同步进度与实现记录。
3. 开发完成后使用 \`$finalize-impact\` 回填影响范围、代码定位、SQL 记录与逻辑流程图。
4. 最后使用 \`$wrap-up\` 做结项校验、验证命令执行与 Commit 信息生成。

## Commands

### $init-task [options] [context]
**Description**: 初始化研发任务规格书。支持全自动分析或手动创建。

**Execution Logic**:
1. **模式判定**：检查 \`options\` 是否包含 \`--auto\`。
2. **任务目录解析**：
    - 先读取项目级提示词、\`AGENTS.md\` 或同级项目规则文件，抽取其中声明的文档默认目录与历史目录。
    - 若项目级规则已明确任务文档目录，例如 \`.codex/tasks/\`，则直接使用该目录。
    - 若项目级规则未定义，再按回退顺序查找 \`.codex/tasks/\`、\`.codex/docs/tasks/\`、\`.claude/tasks/\`、\`.claude/docs/tasks/\`、\`docs/tasks/\`。
- 若均不存在，则创建 \`.codex/tasks/\`。
3. **[手动模式]** (无 \`--auto\`)：
    - 提取 \`context\` 作为任务标题。
    - 在解析出的任务目录下生成 \`task-{{DATE}}-[TITLE_SLUG].md\`；若标题为空则退化为 \`task-{{DATE}}.md\`。
    - 填充内置 \`TASK_SPEC_TEMPLATE\` 模板。
    - 若项目中已存在 \`AGENTS.md\`、\`.claude/tasks/REQUIREMENTS.md\` 或同类约束文档，则自动吸收其中的接口规范、DTO/VO 约束、数据库同步要求写入模板。
    - 立即进入文档编辑态，允许用户补充业务背景。
4. **[全自动模式]** (带 \`--auto\`)：
    - **Context Analysis**：扫描当前对话历史及 \`AGENTS.md\`。
    - **Repo Scan**：扫描 \`Controller\`、\`Service\`、\`Mapper\`、\`sql/\`、任务文档目录，识别 DTO 遗漏点、接口风格差异、潜在 SQL 变更点。
    - **Auto-Fill**：根据分析结果填充模板中的 \`[TITLE]\`、\`[DESC]\`、\`[MODULES]\`、优先级分批与初始风险项。
    - **Commitment**：生成文件后，自动进入开发执行流程；若环境支持多代理，则按任务书执行并行开发。

---

### $sync [description]
**Description**: 增量更新当前任务文档的进度、实现记录与阶段性影响说明。

**Execution Logic**:
1. 定位当前活动任务文档，按“最近修改的 \`task-*.md\`”规则选择目标文件。
2. 读取最新代码变更、文件改动、最近新增的接口/服务/SQL，并与任务清单交叉比对。
3. **进度打勾**：将已完成的任务项更新为 \`[x]\`；未完成项保留 \`[ ]\`。
4. **沉淀记录**：在“实现记录与排错”区块末尾追加 \`description\`。
5. **阶段性总结**：若本轮已经出现明显的影响范围变化，可同步更新“交付影响总结”中的模块或核心变更说明。
6. 若 \`description\` 包含“修复”“排查”“回滚”“兼容”等关键词，优先在记录中强调问题、原因、处理方式和最终结果。

---

### $finalize-impact [description]
**Description**: 在开发完成后自动收口交付影响范围，补充文件定位、数据库变更记录与 Mermaid 逻辑流程图。

**Execution Logic**:
1. 定位当前活动任务文档。
2. 扫描本轮改动文件，优先参考：
    - Git diff / 工作区改动文件
    - 新增或修改的 \`Controller\`、\`Service\`、\`Mapper\`、\`Mapper.xml\`、\`sql/*.sql\`
    - 任务实现记录中出现的核心类、方法、接口、表名、缓存键
3. 回填“交付影响总结”区块：
    - 影响模块
    - 影响类型（接口 / 服务 / 持久层 / 数据库 / 缓存 / 权限 / 文档）
    - 核心变更摘要
4. 回填“文件与代码定位”区块：
    - 使用 \`path:line\` 记录主类、主方法、关键 SQL、关键 XML 语句位置。
    - 每条记录都附带一句说明“这个位置改了什么”。
5. 回填“数据库变更记录”区块：
    - 若检测到 \`sql/\` 脚本、DDL、初始化数据或核心 SQL 变更，则提取关键 SQL 语句或摘要写入文档。
    - 若只是普通查询条件微调，也应至少记录受影响的 Mapper/XML 位置与 SQL 意图。
    - 若未涉及数据库修改，写明“无数据库变更”。
6. 生成“逻辑流程图”区块：
    - 默认输出 Mermaid \`flowchart TD\`。
    - 图中至少包含：入口层、核心服务层、持久层/外部依赖层。
    - 若存在缓存、权限校验、审计、事务、异步、分支判断，应以辅助节点或注释分支展示。
    - 若是多角色、多时序交互场景，可改用 \`sequenceDiagram\`。
7. 若传入 \`description\`，将其写入“交付影响总结”或“实现记录与排错”末尾，作为最终收口说明。

**Output Rules**:
- 文件定位不少于 3 条；大任务不少于 5 条。
- 若涉及数据库改动，SQL 摘要优先保留关键 \`CREATE / ALTER / INSERT / UPDATE / DELETE\` 语句，而不是只写“已修改数据库”。
- Mermaid 图保持 5 到 10 个节点，保证可读性，避免把所有细节都塞入图中。

---

### $wrap-up
**Description**: 结项校验，完成文档收口并生成 Commit。

**Execution Logic**:
1. 校验任务文档中所有 \`[ ]\` 是否已完成；若未完成，明确列出剩余项和阻塞原因。
2. 若“交付影响总结”“文件与代码定位”“数据库变更记录”“逻辑流程图”仍为空，先自动执行一次 \`$finalize-impact\`。
3. 运行 \`mvn -q install\`、\`mvn -q -pl ruoyi-admin -am -DskipTests compile\` 或项目定义的验证脚本。
4. 将验证命令、结果、失败原因或跳过原因回写到任务文档的“验证记录”中。
5. 基于“实现记录与排错”“交付影响总结”“数据库变更记录”生成符合 Git 规范的 Commit Message。
6. 若本轮包含 SQL 变更，结项摘要中必须显式说明“涉及数据库脚本变更”。
