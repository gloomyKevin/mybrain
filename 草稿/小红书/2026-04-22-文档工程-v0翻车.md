### 正文（v0，~600 字）

我最近在 linux.do 翻帖子发现一件怪事：

同样在聊"AI 协作时代怎么管项目文档"，两个高赞帖子的结论**完全相反**。

**重派**（31 赞）说：AI 写代码越写越跑偏，是因为它没边界。你得建一套"文档工程"——
- 规范层（AI 该怎么协作）
- 过程层（这次任务做了什么、改了哪些模块）
- 成品层（系统当前长什么样、对外暴露哪些接口）

配套一整套 AGENTS.md 骨架 + `.codex/` 目录 + 任务模板。

原话是这样的：
> "文档工程不是为了制造更多文件，它是为了让知识具备结构、边界、演进路径和可追溯性。"

**轻派**（另一帖下的反对票）说：
> "好的代码是不需要文档的。文档多了也是屎山。最后用也不会用。"
> "代码 > 注释 > CLAUDE.md > 文档。AI 基本不会去看长文档，看了也是浪费上下文。"

---

两边都有人点赞。到底谁对？

我的判断是：**两派都对，但场景完全不一样**。

| | 重派 | 轻派 |
|---|---|---|
| 适合 | 多人协作 / 长期维护 / 业务复杂 | 一人项目 / 周期短 / 代码动态 |
| 例子 | 企业后端（原帖就是 Java Controller/Service/Mapper） | 独立开发者 / 前端 vibe coder |
| 核心手段 | 三层分离 + AGENTS.md 骨架 | 一个 CLAUDE.md + 子目录继承 |
| 关键取舍 | 结构换可推理性 | 简洁换迭代速度 |

---

对前端 vibe coder（比如我自己），我现在的选择是**偏轻派**：

① 根目录 CLAUDE.md 只写 3 件事：技术栈 / 禁改文件 / 提交前自检
② 和 AI 对话出来的需求讨论类文档——用完就删，不进 Git
③ "本次修复了什么"类文档不留——有人说得对："别在项目里拉屎"

理由很简单：**一个人写代码，文档的首要读者是 AI 不是人**。AI 已经能扫代码，维护一份重型文档工程的 ROI 太低。

## 备注 / 思路演化

**v0 的立场选择**：选了"偏轻派"的判断，理由：
- 和 OPC 规划 Month 1-2 "不加新工具、不重构架构"硬约束方向一致，你能真心相信
